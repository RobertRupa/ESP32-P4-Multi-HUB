# H2-to-P4 UART Diagnostic Audit

## Authorization and target

- Date: 2026-11-08
- User-selected targets and ports: H2 `/dev/ttyACM1`, P4 `/dev/ttyACM0`
- Test: temporary H2 UART0 PING transmitter and P4 UART1 raw-byte receiver
- Rate and format: 230400 baud, 8N1, no flow control
- Wiring: existing user-reported Grove TX/RX/GND test wiring; no pins or cables were changed during this test

## Images and commands

- H2 diagnostic image: `firmware/h2/build-uart-diagnostic/hub_h2_zigbee_rcp.bin`
- P4 diagnostic image: `firmware/p4/build-uart-diagnostic/hub_p4_esp_hosted_host.bin`
- H2 flash command: `idf.py -B build-uart-diagnostic -p /dev/ttyACM1 flash`
- P4 flash command: `idf.py -B build-uart-diagnostic -p /dev/ttyACM0 encrypted-flash`
- P4 flash encryption is enabled on this board. An initial plaintext `flash` attempt caused ROM `invalid header` messages and watchdog resets. Recovery used `encrypted-flash` with `--encrypt`; no full-chip erase or eFuse programming command was run.

## Results

- H2 booted the diagnostic firmware and logged `UART diagnostic ready: UART0, 230400 8N1`.
- H2 accepted each PING write through its UART driver and reported at least 113 sequential ACK timeouts. No matching ACK was received.
- P4 booted the encrypted diagnostic image and logged `UART diagnostic ready: UART1, TX=26 RX=27, 230400 8N1`.
- During more than 100 seconds of observation, P4 repeatedly reported `RX idle bytes=0 pings=0 crc_errors=0`. No raw bytes arrived at the configured P4 RX input, so this run does not confirm the end-to-end UART link.
- ESP-Hosted also auto-initialized the onboard C6 independently of the diagnostic `app_main()` path; its SDIO link came up. This did not produce any UART RX bytes.
- The evidence localizes the failure to the H2-TX-to-P4-RX path as configured, but does not distinguish a physical connection/pin issue from a signal-level or peripheral-routing issue. No hardware pins were reassigned based on inference.

## Restoration

- H2 restored with `firmware/h2/build-default-validation/hub_h2_zigbee_rcp.bin`; esptool verified bootloader, application, and partition table hashes. Boot log confirmed `H2 radio RCP started`.
- P4 restored with `firmware/p4/build-default-validation/hub_p4_esp_hosted_host.bin` using `encrypted-flash`; encrypted writes do not provide normal plaintext read-back hash verification. Boot log confirmed flash encryption, the normal P4 runtime, and matching ESP-Hosted host/C6 version 3.1.0.
- No Zigbee network formation, Spinel handshake, or device join was tested or is claimed.

## Retest after RX/TX swap

- Date: 2026-11-08; same user-selected ports and diagnostic images as above.
- H2 again logged `UART diagnostic ready: UART0, 230400 8N1` and repeated ACK timeouts (at least 113 observed after its monitor was opened).
- P4 again logged `UART diagnostic ready: UART1, TX=26 RX=27, 230400 8N1`; over 100 seconds it repeatedly reported `RX idle bytes=0 pings=0 crc_errors=0`.
- Swapping RX/TX did not change the result. No bytes reached P4 UART1 RX in this test, so the end-to-end link remains unverified.
- After the retest, H2 was restored to the standard RCP with esptool hash verification. P4 was restored to the standard C6-backed runtime using `encrypted-flash`; boot logs confirmed flash encryption, the normal host app, and matching host/C6 ESP-Hosted 3.1.0. No full-chip erase or eFuse programming command was run.

## Test after H2 module-pin clarification

- The user supplied the ESP32-H2-MINI-1 pin diagram: module pin 30 is `RX0`, and module pin 31 is `TX0`. These are module-pad numbers, not GPIO30/GPIO31. The diagnostic remains configured for UART0 RX=GPIO23 and TX=GPIO24, the ESP-IDF H2 UART0 GPIO mapping.
- The H2 UART diagnostic was flashed to `/dev/ttyACM1` and the P4 receiver to `/dev/ttyACM0`; the P4 write used `encrypted-flash`. H2 flash hashes were verified by esptool.
- P4 again logged `UART diagnostic ready: UART1, TX=26 RX=27, 230400 8N1` and repeated `RX idle bytes=0 pings=0 crc_errors=0` for more than 275 seconds. No PING or raw byte was observed after the module-pad numbering was clarified.
- The H2 USB console could not be opened during this run because `/dev/ttyACM1` was exclusively held by another `code` process. The diagnostic image itself remained installed and running; the previous run had already confirmed its PING transmit loop and ACK timeouts.
- Per the user's request, both diagnostic images were left installed after this run. No normal firmware was restored afterward.
- A later P4 monitor capture continued to show zero RX bytes and recorded `BOD: Brownout detector was triggered` after about 71 seconds of that boot. USB Serial/JTAG disconnected, then reconnected to a restarted P4 diagnostic app, which again reported zero RX bytes. Long-run UART conclusions should account for this P4 power/reset instability.

## Source-tagged echo test

- The diagnostic protocol was extended with H2/P4 sender IDs so a frame looped back to its own transmitter can be distinguished from a peer PING or ACK. Host protocol tests and both diagnostic firmware builds passed before flashing.
- Updated H2 diagnostic was flashed to `/dev/ttyACM1`; updated P4 diagnostic was flashed to `/dev/ttyACM0` with `encrypted-flash`. Both USB Serial/JTAG monitors were started.
- The user confirmed the normal H2-to-P4 connection was present and the H2 TX0/RX0 short was removed for this run.
- H2 logged repeated `PEER PING ... ACK sent` entries for P4 frames, but continued to log `ACK timeout` for its own PINGs. This confirms P4-to-H2 reception and H2's ACK writes; it does not confirm H2-to-P4 reception.
- P4 logged 15 `LOCAL ECHO` frames from its own source ID (90 RX bytes), while `pings=0` and `crc_errors=0`. No H2-origin PING or ACK was seen. Thus the observed P4 echo is local to the P4 UART path, not proof of H2-to-P4 traffic.
- The GPIO scan was not implemented. GPIO26/27 and the MAX485 enable path were left unchanged; the project does not identify a safe DE/~RE GPIO. Both diagnostic images and monitors remain active at the user's request.
- User measurement during operation: the MAX485 `DE/~RE` control node was at 0 V relative to GND. If DE and active-low `/RE` are tied to this node, that state disables the MAX485 line driver and enables its receiver. UART1 GPIO26/27 are shared with the MAX485 path; the MAX485 RO output may therefore load or contend with the direct H2-to-P4 RX net. The exact DE, `/RE`, and RO net wiring/GPIO is not established by this measurement alone. No GPIO was driven or changed based on it.
